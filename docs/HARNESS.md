# STory 개발 하네스

## 목적과 근거
에이전트가 제품 의도, 코드 구조, 실행 결과를 직접 읽고 수정할 수 있는 작은 개발 환경을 유지한다. 참고: [OpenAI 하네스 엔지니어링](https://openai.com/ko-KR/index/harness-engineering/). 대규모 팀 사례의 자동 병합, 관측 시스템, 정기 에이전트를 그대로 도입하지 않는다.

## 역할
고정 역할과 전용 스킬의 실제 경로는 [AGENT-TEAM.md](AGENT-TEAM.md)를 따른다. 첫 실행 대기 조건은 [goal-proposal.md](plans/goal-proposal.md)에 기록한다.
- 메인: 요구사항과 파일 소유권 결정, 공통 파일 수정, 통합, 최종 검증.
- UI 담당: 지정된 화면과 스타일 구현, 모바일·키보드 사용 검토.
- 흐름 담당: 지정된 상태/목업 데이터/저장 로직 구현.
- 검토 담당: 기본 읽기 전용. 재현 조건·영향·파일 위치를 보고. 읽기 전용 지시는 협업 규칙이며 실제 도구 권한 격리와 구분한다.
- 현 세션은 메인 포함 동시 4명. 매번 전원을 호출하지 말고 독립된 유용한 작업만 위임한다. 모델은 별도 요구가 없으면 상속한다.

## 위임 계약
서브 에이전트를 실행할 때 아래를 명시한다.
1. 구체적인 목표와 필요한 문서.
2. 담당 파일, 읽기/수정 여부, 제외 범위.
3. 기대 산출물과 확인 방법.
4. 반환 내용: 변경 파일, 근거, 검사 결과, 남은 문제.
공유 브라우저는 한 작업자만 조작한다. 병렬 작업 중 동일한 의존성 설치나 공통 빌드를 중복 실행하지 않는다.

## 개발 루프
요구사항 확인 → 필요한 경우 실행 계획 작성 → 독립 작업 위임 → 구현 → 해당 변경 검증 → 독립 검토 → 근거 있는 문제 수정 → 통합 검증 → 결과 보고.

같은 실패에 같은 명령을 반복하지 않는다. 반복 실패 시 로그/환경/누락 지침을 조사하고 접근을 바꾼다. 외부 접근이나 사용자 판단이 필요한 경우 원인과 가능한 선택지를 보고한다. 목표가 충족되면 검토를 무한 반복하지 않는다. 검토자의 만족 자체보다 재현 가능한 완료 기준을 사용한다.

## 지식 유지
제품 결정은 PROJECT-BRIEF, 코드 경계는 ARCHITECTURE, 실행/검증 근거와 부채는 QUALITY에 기록한다. 여러 파일·에이전트가 관여하는 작업은 `docs/plans/`에 목표, 담당 파일, 진행, 결정, 검증 기록을 남긴다. 사소한 수정에는 별도 계획 파일이 필요 없다. 작업 종료 시 관련 문서의 실제 코드 일치 여부를 확인한다. 예약 자동화는 설정하지 않는다.

## 실제 강제와 지침의 차이
`npm run verify`는 문서 링크 검사·프로덕션 빌드·타입 검사를 실행하고 실패 시 중단한다. 브라우저 QA, 파일 소유권, 프론트엔드 범위는 현재 에이전트 지침/검토로 확인한다. 문서는 보안 경계가 아니며 자동 검증이나 접근 제어를 구현했다고 주장하지 않는다.
